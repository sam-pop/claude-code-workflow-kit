# Pin Opus at medium, escalate only on failure

Claude Opus 5.5 at `medium` effort should anchor every Claude role in the kit. It is also the most cost-efficient point Anthropic has published. On a SWE-bench Pro subset it solved **92.8% of tasks at $0.22 per solved task**, while Fable 5.1 at `high` solved 92.3% at **$1.19**, about 5.4 times as much for the same result ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). The writer should not run at one fixed effort. It should climb a ladder: start at `medium` and escalate to `high` only when an objective signal fires (a failing check or an unresolved blocking review finding). Anthropic measured this policy at **96–97% solved for about $0.24 per task**, against 95.3% at $0.29 for running everything at `high`, so it is both cheaper and better. The reviewer must never run Opus 5.5 below `medium`, because bug-finding drops 34 points at `low`. Reviewer effort should rise with risk. The security auditor should run at `xhigh`. Fable is worth its price only in low-volume reasoning roles: the planner, the auditor, and the last writer rung in the "max" profile. The cross-vendor Codex reviewer should be `gpt-6.1-sol` at `high` on High-risk diffs and `gpt-6-astra` at `high` for the pre-release pass. Run it as a second opinion to triage, not as a merge gate. Two traps matter most for the repo as it stands today. First, its "standard" writer runs Sonnet with no effort pinned, so Claude Code drops it to Sonnet 5.5's `medium` default, roughly 7 points below `high`. Second, a single `CLAUDE_CODE_EFFORT_LEVEL` environment variable silently overrides every per-role setting proposed here.

## Opus 5.5 at medium undercuts Fable fivefold per solved task

Anthropic's own effort sweep is the best data available. It is internal and Anthropic calls it "directional", but it is consistent. On the SWE-bench Pro subset, Opus 5.5 scored **87.4% at `low` ($0.11 per task), 92.8% at `medium` ($0.21), 95.3% at `high` ($0.29) and 96.7% at `xhigh` ($0.74)** ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). The curve is concave. Going from `medium` to `high` buys 2.5 points for about 40% more money. Going from `high` to `xhigh` buys 1.4 points for 2.5 times the cost. That shape matches independent work on OpenHands agents, which found accuracy peaking at intermediate token spend, and found that the most expensive runs are often failures that keep re-reading and re-editing the same files ([tokenade summary of arXiv 2604.22750](https://tokenade.net/en/case-studies/swe-bench-agent-token-study)). It also matches the "overthinking" result, where reasoning models that deliberate instead of acting resolve fewer SWE-bench tasks ([Cuadron et al.](https://arxiv.org/abs/2502.08235)).

Comparing models shows something effort tuning cannot. **A stronger model at a lower effort often beats a weaker one at a higher effort per solved task.** Sonnet 5.5 at its API default (`high`) and Opus 5.5 at `low` both solved about 87.5%, for $0.11 and $0.12 per solved task. Opus tokens cost twice as much, but Opus finishes with less work ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). Above that level Opus 5.5 pulls ahead and Fable 5.1 does not. On an internal agentic-coding benchmark, Opus 5.5 at `medium` scored 86.6% at $0.84 per attempt and Fable 5.1 at `medium` scored 84.2% at $2.68 ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). On CursorBench, Opus 5.5 at `medium` (52.5%) edged out Fable 5.1 at `max` (51.8%) ([Opus 5.5 launch](https://www.anthropic.com/news/claude-opus-5-5)). Anthropic also tested Fable as an orchestrator, which cost 24% more with no gain, and as an advisor to an Opus executor, which added 1.7 points (within noise) for about 2.1 times the cost. For routine coding, the data gives no reason to put Fable in a high-volume role.

Fable still has a defensible niche. Claude Code's docs point it at "root-cause investigations, outage debugging, and architecture decisions" ([Claude Code model config](https://code.claude.com/docs/en/model-config)). Planning and system-wide security auditing are exactly that kind of work, and both run rarely: once per larger change and once per release. Splitting planning from execution is also well supported. In Aider's architect/editor experiments, a strong planner with a cheaper editor beat the strong model working alone, and even pairing a model with itself improved its score: Sonnet 3.5 went from 77.4% to 80.5% ([Aider](https://aider.chat/2024/09/26/architect.html)). That evidence is from 2024. Anthropic's current advice adds that smaller or cheaper configurations do best with "specific instructions directing execution" ([Claude blog](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)), which is what the kit's blueprint provides. Spending more on the planner is how the writer earns the right to run at `medium`.

Sonnet 5.5 is the warning case. Claude Code runs it at `medium` by default even though the API default is `high` ([Claude Code model config](https://code.claude.com/docs/en/model-config)). At `medium` it gave up **about 7 points on SWE-bench Pro and fell from 77.8% to 62.7% on Anthropic's internal agentic-coding benchmark** ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). A subagent on a different model from the main session does not inherit the session's effort. It falls back to that model's own default ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)). So the kit's current `writer: sonnet`, with no `effort:` line, runs at Sonnet's weakest coding point under an Opus main session. Sonnet 5.5 pinned to `high` is a reasonable fallback writer where Opus allowance is tight. Pinned to `medium` it is a false economy. Haiku 5.5 has no published coding benchmarks, and Anthropic warns that at `low` it is "more likely to skip a search, stop early, or skip a check" in long agent prompts ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort)). It belongs in exploration subagents, not in any of these five roles.

## A medium-to-high ladder beats fixed high on price and pass rate

Anthropic measured escalation directly. On 478 SWE-bench Pro problems, Opus 5.5 was run at one effort and only its failures were re-run at a higher one ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)):

| Policy (Opus 5.5) | Solved | Cost per task |
|---|---|---|
| `low`, failures re-run at `high` | 96.4–97.5% | ~$0.17 |
| `medium`, failures re-run at `high` | 96.0–97.1% | ~$0.24 |
| `high`, failures re-run at `high` | 96.9% | $0.31 |
| everything at `high` | 94.8–95.8% | $0.29 |

**The ladder wins on both axes: 17% cheaper than fixed `high` when starting at `medium`, 41% cheaper when starting at `low`, and one to two points more tasks solved.** Anthropic credits the saving to the policy and states the precondition plainly: you need a reliable failure signal. The broader literature agrees and adds two refinements. First, returns from extra attempts flatten fast. The first retry adds the most, gains are moderate from two to four attempts, and they plateau by four to eight without a good selector. A CMU study puts the ceiling around three to seven retry turns before context pollution dominates ([Codex CLI blog summary of arXiv 2604.16529 and 2602.18998](https://codex.danielvaughan.com/2026/06/20/scaling-test-time-compute-agentic-coding-codex-cli-rollout-retry-rtv-pdr-strategy/)). Second, escalating is not always the right recovery. In CodeRescue's oracle analysis of failed cheap attempts, **28% were solvable only by cheap self-repair, 45% only by escalating to the stronger model, and 27% by either** ([CodeRescue](https://arxiv.org/html/2607.19338v1)). On the hardest tier, neither model succeeded reliably. That makes a stop rule as important as the rungs.

The kit should start the ladder at `medium`, not `low`, even though `low` measured cheaper. The difference is the failure signal. SWE-bench grades against hidden tests the agent never sees. In the kit, the writer writes its own tests, and the reviewer, at best-in-class AI review recall of roughly 50–70%, misses a third to half of real bugs ([Greptile on Martian](https://www.greptile.com/content-library/greptile-martian-code-review-benchmark); [Unblocked](https://getunblocked.com/benchmarks/code-review/)). A low-effort attempt that passes its own thin tests never triggers escalation. It escapes. Anthropic's defect-search result points the same way: Opus 5.5 at `low` scored 34 points below `medium` at finding bugs ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)), which suggests (as an inference) that low-effort self-checking is weak. The price of the safer start is about $0.07 per task, a rounding error next to one escaped defect. Claude Code's own guidance also maps `medium` to "day-to-day engineering work with a clear scope, such as implementing a new feature," which is what a blueprint-driven writer task is ([Claude Code model config](https://code.claude.com/docs/en/model-config)).

The rungs are: **`medium` → `high` → a third rung of Opus 5.5 `xhigh` (standard) or Fable 5.1 `high` (max) → stop and re-plan.** The third rung is the least supported step. No repository-level study measures a model-switch rung. Fable 5.1 at `high` scored below Opus 5.5 at `high` on the SWE-bench Pro subset. The case for using it as the max-profile rung rests on two things: changing the model on residual failures (CodeRescue's 45% bucket), and Anthropic's own positioning of Fable for root-cause work. Treat that rung as a hypothesis for the first month to test. After the third rung, the ladder ends. A blueprint that defeats three attempts goes back to the planner with the failure briefs, and the owner is told.

Triggers must be objective, and the ordering of evidence is clear. Test or judge failure is strong. Repeated-failure ("stuck") detection is plausible. Model self-assessment is weak, because overconfident wrong answers suppress needed escalations ([arXiv 2608.24087](https://arxiv.org/pdf/2608.24087)) and executors rarely ask for help even when they can: one Opus 5.5 advisor run consulted on 1 of 300 tasks ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). The kit already produces the strong signals: `scripts/check.sh` exit codes in the writer's report, and the reviewer's independent re-run of lint and tests compared against the base branch. Claude Code has no documented loop detector, so the stuck thresholds should come from OpenHands, which has the best-documented one: **three identical errors, four identical action-observation pairs, three no-progress monologue turns, or six ping-pong cycles** ([OpenHands](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)). Following CodeRescue's split, a reviewer's blocking finding should first get one cheap repair pass at the same rung, and escalate only if that pass fails to clear it.

Escalation has a switching cost, and the handoff design controls it. Changing top-level effort mid-conversation forced Anthropic's test to rewrite 81K of a cached 101K-token context. On Fable 5.1 that request cost $1.02, against $0.025 for a per-message effort change ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). In Claude Code the clean boundary is a **fresh writer invocation** through the Agent tool. The tool accepts a per-call `effort` (v2.1.292+) and a `model` alias such as `fable` ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)). Seed the new writer with a compact failure brief, not the old transcript. The brief covers:

- the failing check and the tail of its output,
- the hypotheses tried,
- the files touched,
- the failed diff saved as a commit or patch.

This mirrors Anthropic's long-running-agent harness, which hands state between context windows through git commits and a progress file ([Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)), and the RTV method, where structured summaries outperformed full rollouts ([summary](https://codex.danielvaughan.com/2026/06/20/scaling-test-time-compute-agentic-coding-codex-cli-rollout-retry-rtv-pdr-strategy/)). Do not resume the failed writer: its context carries the framing that failed.

## Review quality collapses below medium, so effort rises with risk

Review is the role where effort matters most and where cutting it is most dangerous. Opus 5.5 lost 34 defect-search points from `medium` to `low` for about a fifth of the cost. Fable 5.1 lost only 1.8 points from `high` to `low` ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). OpenAI's code-verification study adds what extra budget buys a reviewer. Even a small budget recovers many known high-severity issues, and more budget "mostly improves calibration and reduces false alarms" ([OpenAI](https://alignment.openai.com/scaling-code-verification/)). For a single-owner kit, false alarms are the real cost, because every one is a finding the owner must triage. The same study found that recall drops faster at low budget on **model-written code than on human-written code**. Every diff in this kit is model-written, which argues for review effort above the default, not below it. Self-preference research points the same way. Judges favor their own wrong answers on code tasks roughly 50–75% of the time for large models, and long chain-of-thought gave the lowest harmful self-preference of any setting tested ([arXiv 2504.03846](https://arxiv.org/html/2504.03846v3)). The kit's reviewer already reads the diff before the plan, in a separate context. Running it at `high` is the second, evidence-backed defense against Opus grading Opus.

Scaling effort by risk follows Anthropic's own split. `high` is for "work where verification matters or edge cases are likely," and `max` is for "hard problems you want Claude to work through without you, such as finding security vulnerabilities," with a warning about overthinking ([Claude Code model config](https://code.claude.com/docs/en/model-config)). The kit has no risk tiers today, so this report proposes three, built from areas the planner already lists under "Hard parts":

- **Low**: a small fix in the main session.
- **Medium**: a normal blueprint change.
- **High**: anything touching authentication or authorization, tenancy, money movement, personal or financial data flows, secrets, migrations or destructive writes, concurrency, or the kit itself (`.claude/`, `scripts/`, CI).

High-risk diffs get `xhigh` review. Any writer output that needed escalation is reviewed one tier up, because escalation is direct evidence the task was harder than planned. `max` stays out of the defaults. Sonnet 5.5 scored lower on FrontierCode at `max` than at `xhigh` because extra review passes caused timeouts and out-of-scope edits ([Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5)), and no published ablation compares `xhigh` with `max` for review or for finding vulnerabilities.

The security auditor has the strongest case for depth and the clearest need for validation. Frontier models with agentic scaffolding found **more than 500 validated zero-days** in open-source code (Opus 4.6, each one human-validated) ([Anthropic red team](https://red.anthropic.com/2026/zero-days/)). Meanwhile, project-scale studies of LLM vulnerability detectors still report high false-discovery rates, rooted in shallow interprocedural reasoning ([arXiv 2601.19239](https://arxiv.org/pdf/2601.19239)). The gap is best explained by scaffolding and validation rather than by the model alone. That points to `xhigh` on Opus in the standard profile, to Fable 5.1 at its default `high` in the max profile (Fable gains little from more effort on defect search, so `xhigh` or `max` there is poor value), and to a requirement that a Critical or High finding come with a reproduction (a failing test, a trace or a concrete path) before it blocks a release.

## Codex earns a seat as a dissenting opinion, not a gate

The argument for a reviewer from a different vendor rests on solid mechanism and no direct measurement. Across 350+ models, those sharing a provider or architecture make more correlated errors. But "larger, more accurate models have highly correlated errors even with distinct architectures and providers" ([Kim et al., ICML 2025](https://arxiv.org/html/2506.07962v1)). No controlled study counts the extra true defects a GPT-family reviewer finds in Claude-written code. The Codex-specific quality data is thin and predates GPT-6. CR-bench scored Codex at 20.1% against Claude Code's 32.1%, without stating models or effort ([CR-bench summary](https://codex.danielvaughan.com/2026/05/02/code-review-agent-benchmark-cr-bench-codex-cli-review-quality/)). OpenAI publishes no precision figures and tells users to check each finding "against the latest diff, expected behavior, and tests" ([Codex code review](https://learn.chatgpt.com/docs/code-review)). The honest reading is that Codex is not a better reviewer than the Claude reviewer. It is a *different* one. Its value is in the findings the Claude reviewer did not raise. Practitioners use exactly that heuristic: "Where Codex and Claude agree, that's signal. Where they diverge, that's the line I read myself" ([Zack Proser](https://zackproser.com/blog/codex-reviews-claudes-diffs)). For the marginal review dollar, that diversity argument favors Codex over a second same-provider pass on Fable.

On model choice, `gpt-6.1-sol` dominates for routine use. It costs **$2 input / $10 output per million tokens, a fifth of `gpt-6-astra`'s $10 / $50** ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)). On DeepSWE 1.1 at High effort it scored 75.2% at $0.65 per task, against Astra High at 73.2% and $3.92 (OpenAI launch figures via a [secondary summary](https://kingy.ai/blog/gpt-6-1-sol-specs-benchmarks-pricing-task-costs/); the primary page could not be fetched). OpenAI's headline coding number for Sol is at High, which makes `high` the natural effort for High-risk diffs. Astra's lead appears on harder, longer tasks: **68.1% against Sol's 57.0% on Terminal-Bench Science at Max, for 4.4 times the cost** (same secondary source). That fits a pre-release pass over a whole release's diff, which runs rarely and covers more cross-cutting changes. Astra on ChatGPT Plus is limited to roughly 5–45 local messages per five hours ([Codex pricing](https://learn.chatgpt.com/docs/pricing)), which is enough for one pass. Where Astra is unavailable, fall back to Sol at `xhigh`. Never use `ultra`: in Codex it fans the work out to subagents ([Codex models](https://learn.chatgpt.com/docs/models)), so cost and latency are unbounded and the output is harder to reproduce.

Mechanically, `codex exec` is the safer scripted route. Unlike `codex review`, it documents `--output-schema` and `-o` for machine-readable findings, and it runs read-only by default ([Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)). Pin the model and effort explicitly, because the CLI's default effort for Sol is not documented. A typical call looks like `codex exec -m gpt-6.1-sol -c model_reasoning_effort="high" -s read-only --ephemeral --ignore-user-config --output-schema review.schema.json -o review.json` with the base-branch diff piped in. Run it from the repo root so Codex can read the surrounding code, since repository access measurably strengthens reviewers ([OpenAI](https://alignment.openai.com/scaling-code-verification/)). At list prices, a Sol review that reads 100K input tokens and writes 5K output costs about $0.25 uncached; Astra costs about $1.25. Local reviews draw from the ChatGPT plan's general limits, and an API key bills every token ([Codex pricing](https://learn.chatgpt.com/docs/pricing)). OpenAI warns against setting `CODEX_API_KEY` as a job-level variable in workflows that run repository-controlled code ([Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)).

## Recommended defaults for the kit

These are proposals for the owner. Once accepted, record them in `docs/decisions.md` with the date. The first change is to `scripts/set-models.sh`: it should write an `effort:` line into each agent's frontmatter alongside `model:`, because frontmatter effort outranks the session level and is the only per-role pin that holds up across sessions. Proposed header:

```
#             planner      writer        reviewer     security-auditor
#   standard  opus/high    opus/medium   opus/high    opus/xhigh
#   max       fable/high   opus/medium   opus/high    fable/high
```

| Role | standard (any plan with Opus) | max (plans that include Fable) | Why |
|---|---|---|---|
| planner | Opus 5.5 `high` | Fable 5.1 `high` | Low volume. Blueprint quality decides whether the writer succeeds at `medium`. Fable is positioned for architecture decisions. |
| writer | Opus 5.5 `medium`, then the ladder | Opus 5.5 `medium`, then the ladder | Best measured cost per solved task. Replaces the unpinned `sonnet` writer, which runs at Sonnet's `medium` default. Fallback where Opus allowance binds: Sonnet 5.5 pinned `high`. |
| reviewer | Opus 5.5 `high` (default), scaled by risk | Opus 5.5 `high`, scaled by risk | Per-change volume makes Fable's ~5x cost hard to justify without review-specific evidence. The High-risk second opinion comes from Codex. |
| security-auditor | Opus 5.5 `xhigh` | Fable 5.1 `high` | Rare, high stakes. Fable barely gains from more effort on defect search. |

The current "max" profile puts Fable on the reviewer and Opus on the planner. This report reverses both choices: Fable goes where the work is rare and architectural, and per-diff review stays on Opus.

| Writer rung | standard | max | Enter when |
|---|---|---|---|
| 1 | Opus 5.5 `medium` (frontmatter) | same | Always |
| 2 | Opus 5.5 `high`, fresh invocation with failure brief | same | Any trigger below |
| 3 | Opus 5.5 `xhigh` | Fable 5.1 `high` (Agent tool `model: fable`) | Rung 2 hits a trigger |
| stop | Return to planner with all briefs; tell the owner | same | Rung 3 hits a trigger |

Escalate on any of these triggers:

- A `scripts/check.sh` lint, test or build failure remains after the writer's own repair loop.
- The reviewer's re-run disagrees with the writer's reported exit codes, or test counts fall below the base branch.
- A blocking reviewer finding survives one same-rung repair pass.
- The same check fails with the same error three times.
- The same file is edited four or more times without the test outcome changing.
- Token spend for the rung exceeds three times that rung's running median. Calibrate this one during the first month.

These do not trigger escalation: the writer's own sense of difficulty, non-blocking Warnings, and an "unverified" status caused by a check that is NOT CONFIGURED, which is a setup gap rather than a capability gap.

| Risk tier | Definition | Reviewer effort | Codex | Auditor |
|---|---|---|---|---|
| Low | Small fix in main session (1–2 files, reversible) | `medium` (via Agent tool `effort`) | none | — |
| Medium | Blueprint change touching no sensitive area | `high` (frontmatter default) | none | — |
| High | Auth/authz, tenancy, money, personal or financial data, secrets, migrations or destructive writes, concurrency, kit files; or any escalated writer output | `xhigh` | `gpt-6.1-sol`, `model_reasoning_effort="high"` | on request |
| Release | Pre-release, and quarterly | — | `gpt-6-astra` `high` (fallback `gpt-6.1-sol` `xhigh`) | standard: Opus `xhigh`; max: Fable `high`. Critical/High findings need a reproduction to block. |

The planner should state the tier in its blueprint, and the main session confirms it. Codex output is triaged against the Claude reviewer's findings. Agreement raises confidence, and findings only Codex raised get the owner's attention. Codex findings alone never block.

## Configuration traps and evidence gaps that can quietly undo this

Claude Code's effort precedence is the biggest operational risk. The environment variable `CLAUDE_CODE_EFFORT_LEVEL` beats everything else, including the Agent tool's per-call `effort` and subagent frontmatter ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)). One stray export flattens the ladder and the risk scaling into a single level without any warning. `scripts/doctor.sh` should warn when that variable is set. It should also warn when `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` is set, since that forces one model onto every subagent and ignores frontmatter, and when Claude Code is older than v2.1.292, which lacks the per-call effort parameter. Several more defaults and limits catch people out ([Claude Code model config](https://code.claude.com/docs/en/model-config)):

- A subagent without its own `effort` on the main session's model inherits whatever `/effort` the owner set. One on a different model falls back to that model's default.
- A top-level `effortLevel` in user settings does not apply to Opus 5.5 at all.
- Neither `effortLevel` nor `modelSettings` accepts `max`.
- An organization's `maxEffortLevel` silently lowers an `xhigh` setting.
- Aliases change by provider. On Bedrock and Google Cloud `sonnet` means Sonnet 4.5, and on Foundry `opus` means Opus 4.6, which has no `xhigh` and quietly runs it as `high`.

Fable billing differs by plan and by how Claude Code runs. On Pro and standard Team seats, Fable is outside the plan's limits and bills usage credits at API rates from the first request. On Max and premium seats, secondary reports say up to 50% of the weekly limit can go to Fable, drawn from the same pool ([Notebookcheck](https://www.notebookcheck.net/Claude-Fable-5-1-is-not-included-in-your-Pro-subscription.1385320.0.html)). In `claude -p` runs, Claude Code bills Fable to credits **without asking**. In background, Remote Control or teammate sessions, the consent prompt waits five minutes and then **drops the turn without sending it** ([Claude Code model config](https://code.claude.com/docs/en/model-config)). A max-profile planner run headless therefore either spends silently or never runs. Owners should set a monthly credit cap through `/usage-credits` ([Claude Code costs](https://code.claude.com/docs/en/costs)).

Security work may also not run on the configured model. "Most cybersecurity tasks are rerouted to Opus 4.8" on Opus 5.5 ([Opus 5.5 launch](https://www.anthropic.com/news/claude-opus-5-5)). Opus 4.8 is an older model with higher per-token prices ($5 / $25) ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Fable's classifiers can send flagged requests to another model at the same effort ([Claude Code model config](https://code.claude.com/docs/en/model-config)). Nobody has documented whether a defensive audit of one's own repo trips these classifiers, so the auditor's served model must be recorded, not assumed.

The evidence has clear limits. Almost every effort and cost figure comes from Anthropic's internal, directional studies on one SWE-bench Pro subset, with single runs at `xhigh` and for Fable. Agent token use on the same task varies up to 30 times between runs ([tokenade](https://tokenade.net/en/case-studies/swe-bench-agent-token-study)). No published data covers planner-specific effort, review or security effort ablations for Claude, or a model-switch escalation rung on repository tasks. No controlled cross-vendor review study exists. The GPT-6.1 Sol benchmark figures come through a secondary summary. The `codex review` flags and Sol's default CLI effort are undocumented. How Anthropic counts plan usage across models is unpublished, so subscription costs here are inferred from API prices.

## What the first month must measure

A single-owner repo will produce tens of writer tasks in a month, not hundreds. Given the 30x run-to-run variance, the experiment can detect large effects only: a rung that rarely rescues anything, a reviewer tier that adds nothing, a Codex pass that never finds anything new. Compare medians, not means. The review log the kit already keeps (`docs/reviews/`, with fixed and dismissed findings, and the agreement rate `doctor.sh` prints) is the natural base. Add one line per task recording the risk tier, the rung reached, the trigger that fired, and the model and effort shown by `/tasks`. Take per-subagent spend from `/usage`, which attributes usage to subagents ([Claude Code costs](https://code.claude.com/docs/en/costs)).

| Measure | Decision rule at month end (proposed) |
|---|---|
| Rung-1 clearance rate: writer passes checks and review with no escalation | Below 70%: fix blueprint quality or start at `high`. Above 95% over 15+ tasks: trial `low` as rung 1 on well-tested areas next month. |
| Rescue rate of rungs 2 and 3 | Rung 3 rescues fewer than one in three of its entries: drop it and go straight to re-plan. |
| Median cost and wall time per completed task, by rung | Sets the "3x median" budget trigger. |
| Reviewer accepted-finding rate (fixed vs dismissed) by effort tier | `xhigh` on High-risk shows no higher acceptance or catch rate than `high`: drop it to `high`. |
| Escaped defects traced to a reviewed change | Any High-risk escape: revisit the tier definitions before the costs. |
| Codex unique accepted findings, false-positive rate, agreement rate | No unique accepted finding across 8+ High-risk diffs: move Codex to pre-release only. |
| Auditor served model, and reproduced vs unreproduced Critical/High | Run `xhigh` and `max` once each on the same release commit and count validated findings. Note any reroute. |
| Fable credits spent and share of the weekly limit; consent-prompt drops | Fable consumes a large share of the weekly window: move the planner back to Opus `high`. |

## Conclusion

The main lever in this research is not effort at all. It is the quality of the failure signal. Every cost saving above depends on the kit knowing when an attempt failed. In this kit the writer writes its own tests, so the reviewer's independent re-run and the stuck counters are what make the ladder safe. Investing in those signals pays off more than any setting in `set-models.sh`. The same logic changes where premium models belong. A stronger model pays off where its output gates many cheaper steps (the blueprint) or where a single miss is expensive and rare (the audit), not in the high-volume middle of the loop.

The second takeaway concerns independence. Same-provider review at high effort and in a fresh context already captures most of what the evidence can prove. A different vendor is the cheapest remaining source of *uncorrelated* judgment, which is why Codex at Sol `high` is a better use of the marginal review dollar than Fable. The numbers in this report are directional and will drift with each model release. The month-one log is how the kit replaces them with its own.
